The Problems We Solve

Building reliable applications on top of LLMs and autonomous agents reveals operational pain points across tools, auth, reproducibility, and security. Here is what Trooth does about each:

Problem Today Trooth Solution
Tool sprawl: one MCP server per data source, dozens of tool schemas eating the context window One server, six tools, dynamic resolution across catalog sources
Auth sprawl: separate OAuth flows and credential stores for each individual upstream One key to Trooth; pass-through credentials stored encrypted per customer
No provenance: agent cannot tell how fresh or how trustworthy a returned value is Every response is an envelope: source identity, timestamps, freshness lag, lineage, and scorecard link
Silent revisions: upstream modifications break backtests and invalidate cached conclusions Append-only snapshot history, revision diffs, and alerts when values or schemas shift
Prompt injection: untrusted free text from upstream lands directly in the agent context Structured data payload; upstream free text is quarantined in an untrusted text block
Non-reproducible results: same query yields different answers tomorrow with no record why Content hash and snapshot id in every envelope; fetch accepts as-of parameter to replay past state
No cost visibility: lack of quota feedback inside autonomous execution loops Remaining quota, unit cost, and cache status returned inside every envelope
Discovery confusion: unclear which feeds are primary authorities and which are lagging republishers Mechanical lineage inference based on observed publication lag published on public scorecards
Data monetization barrier: data owners lack an easy way to sell feeds or filters to agents Provider listing with automated metering, cryptographic provenance, and a public scorecard included

How It Works: The Single Connector

Trooth sits between the caller and the universe of real-world data feeds, executing a deterministic 4-step pipeline:

Step 1

Resolve

Query is matched against catalog entries and performance scorecards. Trooth picks primary feeds and records rejected alternatives with explicit reasons.

Step 2

Fetch

Retrieves fresh live data from upstream or pulls from the versioned snapshot cache. Replays historical requests via as_of timestamps.

Step 3

Normalize

Transforms raw upstream shapes into standardized schemas. Any free text is quarantined into untrusted_text to prevent prompt injection.

Step 4

Reconcile & Sign

Attaches lineage graphs, field-level disagreements, computes SHA-256 payload digest, and cryptographically signs the envelope with Ed25519.

auditable Routing

considered_and_rejected is mandatory whenever multiple sources exist. It shows why an alternative was bypassed (such as publication lag).

Injection Defense

untrusted_text isolates arbitrary string descriptions from upstream, preventing malicious prompt injections from entering autonomous loops.

Verifiable Signatures

Every envelope is signed with an Ed25519 private key. Anyone can verify authenticity using the public key hosted at /.well-known/trooth.json.

The Six Tools of Trooth

Agent context windows should hold reasoning, not tool schemas. Trooth bounds its interface to exactly six high-density tools. Depth goes into parameters, not new tools:

trooth.resolve

No fetch

Given a natural query or typed request, returns the candidate sources Trooth would select with reasons, and those rejected with reasons.

trooth.fetch

Returns Envelope

Fetches data for a resolved request. Supports parameters: freshness (live, cached_ok, as_of=<snapshot>) and max_sources.

trooth.compare

Reconciliation

Executes the same query across multiple candidate sources simultaneously, returning field-level disagreements with lineage tracking.

trooth.scorecard

6 Dimensions

Retrieves the mechanical six-dimension scorecard for any source, plus anchored accuracy if an independent authority exists.

trooth.catalog.search

Discovery

Filters and searches the verified source catalog by domain, geographic coverage, specific field, license type, or cost model.

trooth.verify

Cryptographic

Verifies an envelope: Ed25519 signature validation, SHA-256 payload hash confirmation, and transparency log checkpoint verification.

Self-specializing nodes that agents attach to. Trooth makes the outside world verifiable; KouroB makes a node's own answers verifiable. The two were built from the same conviction at opposite ends.
